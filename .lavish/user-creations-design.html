User Creations Persistence

Database-backed generation history — survive login/logout, persist across sessions

🧱 Database ⚡ API 🎨 Frontend ☁️ S3
🎯

Goal & Current State

Goal: Every generation a user creates gets persisted to the database. When they log out and log back in, their full history is restored — prompt, settings, generated images, everything.

⚠️ Current State

  • • GenerationHistoryItem lives only in Redux — lost on page refresh or login/logout
  • • Generated images are base64 data URIs — not stored anywhere persistent
  • • No mechanism to load history from a server
  • • Delete & Clear operations only affect in-memory Redux state

✅ Decisions Made

Image Storage

Upload to S3 during generation. Backend handles upload, returns S3 URLs. Follows existing template pattern.

Editor Changes

Update in-place + keep snapshot. Edited images overwrite the creation but previous version is preserved.

S3 vs DB

S3 — do it right. Generated images go to S3, DB stores URLs.

API Changes

MODIFIED POST /api/generate POST /api/generate/video

After Gemini returns images, the backend now also:

  1. Uploads each generated image to S3 (generations/{userId}/{timestamp}-{random}.webp)
  2. Creates a user_creations row with all params + S3 URLs
  3. Returns creationId and s3Urls alongside existing imageUrls
// New response shape
{
  "imageUrls": ["data:image/webp;base64,..."],  // Immediate display (unchanged)
  "s3Urls": ["https://bucket.s3.amazonaws.com/generations/..."],  // NEW
  "creationId": "uuid"  // NEW
}
NEW GET /api/generations

Returns all creations for the authenticated user, sorted newest-first.

NEW DELETE /api/generations/:id

Deletes a specific creation (owner-only). Returns { success: true }.

NEW PUT /api/generations/:id/images

Updates creation images after editor save. Body: { imageUrls: string[] } (data URIs). Backend uploads to S3, updates row, snapshots old URLs in metadata.

Review & Confirm

  • Q1 S3 key prefix: Generations stored at generations/{userId}/{mediaType}/{timestamp}-{random}.{ext} — same bucket as templates, different prefix. The {mediaType} segment keeps images and videos in separate prefixes for future extensibility.
  • Q2 Editor snapshots: ✅ Store in simple JSONB (metadata.previousImages). Extensible enough for complete edit tracing — can always migrate to a separate table later if querying snapshots becomes a bottleneck.
  • Q3 On-mount loading: When /generate page loads — replace Redux history entirely with API data, or merge?

    Trade-offs:

    Replace (API source of truth) Merge (keep in-memory + API)
    Correctness ✅ Perfect — API is authoritative. No stale local state. ⚠️ Can show items the API doesn't know about (e.g., failed saves).
    Simplicity ✅ Replace entire history array. One source of truth. ⚠️ Need dedup logic by creationId. Edge cases with pending generations.
    Fresh generations ⚠️ In-memory items from current session (not yet in DB) would be lost on re-fetch. ✅ Current session's new generations stay visible even before API confirms them.
    Recommendation Merge approach: On mount, fetch API data + prepend to Redux history. But skip any API items that already have a matching creationId in the in-memory history (prevents duplicates after re-renders). This gives us the best of both: persisted creations survive logout, and fresh generations show up instantly.
  • Q4 Video support: Videos are also generated as data URIs. Same S3 upload pattern applies? S3 key: generations/{userId}/{timestamp}-{random}.mp4
