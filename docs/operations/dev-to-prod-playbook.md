# Dev-to-Prod Playbook

> **A reusable guide for taking a Next.js + Express + Supabase Postgres project from local development to production on AWS.**
>
> Created during the ViewCreator production launch (2026-07-08).
> Import this into other projects as a starting template.

---

## How To Use This Guide

This is a **living playbook** — run through it step by step. Each step has:
1. **What** — what we're doing and why
2. **Input needed** — decisions you need to make (marked with 🗣️)
3. **Action** — commands or code changes to execute
4. **Verify** — how to confirm it worked
5. **Learnings** — things we discovered along the way (appended as we go)

---

Before starting, you should have:

- [ ] A working dev environment with the project running locally
- [ ] Git repository set up with your code

## Step 1: Remove Vendor Lock-in from DB Connection

### What

The database connection code may have hardcoded hostname checks (e.g., `.includes('supabase.co')`). Replace these with pure environment-driven configuration. This makes switching DB providers a config change, not a code change.

### Why

- You're using raw `pg` (node-postgres), not the Supabase SDK — you have zero vendor coupling in your queries
- The only coupling is in the connection config. Remove it
- Future: migrating to RDS, Aurora, or any Postgres host = change `DATABASE_URL` + `DB_SSL`

### Action

**Before** — hostname sniffing:
```ts
const isSupabase = databaseUrl.includes('supabase.co');
const ssl = sslMode === 'true' || sslMode === '1' || (isSupabase && sslMode !== 'false') || false;
```

**After** — purely env-driven:
```ts
const ssl = process.env.DB_SSL === 'true' || process.env.DB_SSL === '1';
// Set DB_SSL=true for Supabase or any cloud Postgres
// Set DB_SSL=false for local dev
```

Also update the error message to be provider-agnostic:
```ts
throw new Error(
  'DATABASE_URL is not set. Set it in your environment or .env file.\n' +
  'Example: DATABASE_URL=postgresql://user:password@host:5432/db'
);
```

### Verify

```bash
# With valid DB_URL + DB_SSL=true — should connect
DATABASE_URL=postgresql://... DB_SSL=true npx tsx src/migrate.ts

# Without DB_SSL — should still work for local Postgres (no SSL)
DATABASE_URL=postgresql://localhost:5432/test npx tsx src/migrate.ts
```

## Step 2: Create a Root `.env.example`

### What

Create a single `.env.example` at the project root that documents every environment variable used across all packages.

### Why

- The existing `.env.example` files are scattered across packages and incomplete
- A single source of truth prevents misconfiguration
- Makes onboarding new developers trivial

### Action

1. Search your codebase for all `process.env.*` references:

```bash
grep -r "process\.env\." --include="*.ts" --include="*.tsx" --exclude-dir=node_modules --exclude-dir=.next -h | grep -oP 'process\.env\.\w+' | sort -u
```

2. Document each variable with:
   - Description of what it does
   - Where it's used (which package/file)
   - Whether it's required or optional
   - Example value (never a real secret)

### Verify

- [ ] Every `process.env.` reference in code has a corresponding entry in `.env.example`
- [ ] Required vars are clearly marked
- [ ] The file is committed (no real secrets)

## Step 3: Create Separate Supabase Projects (Dev + Prod)

### What

You need two Supabase projects: one for development, one for production. They should never share a database.

### 🗣️ Input Needed

When you reach this step with your project, you'll need:

1. **Supabase organization** — do you use an existing organization or create a new one?
2. **Project region** — should match your compute region (us-east-1 recommended for AWS)
3. **Pricing tier** — free for dev, Pro ($25/mo) for prod
4. **Database password** — auto-generated by Supabase, store in secrets manager

### Action

**For each project:**

1. Go to [supabase.com/dashboard](https://supabase.com/dashboard) → New project
2. Set name (e.g., `viewcreator-dev`, `viewcreator-prod`)
3. Set database password (store it — shown once)
4. Choose region (match your compute region)
5. Wait for provisioning (~2 minutes)

**Run migrations on prod:**

```bash
cd viewcreator-database
DATABASE_URL=postgresql://postgres:password@db.[ref].supabase.co:5432/postgres npm run db:migrate
```

### Verify

- [ ] Dev project accessible from local dev environment
- [ ] Prod project accessible (test with health check or a simple query)
- [ ] Both have same schema (run `npm run db:migrate` against both)

## Step 4: Use Supabase Connection Pooler (PgBouncer)

### What

Supabase Pro includes PgBouncer connection pooling. Use the pooler URL (port 6543) for the API server, direct connection (port 5432) for migrations.

### Why

- Direct connections are limited (~60 per vCPU on Pro)
- PgBouncer pools connections efficiently — set your app's pool `max` to 20+ without exhausting Postgres
- The pooler handles connection storms from serverless/container restarts

### Action

Update your production env vars:

```
# API server (uses pooler — port 6543):
DATABASE_URL=postgresql://postgres:password@db.[ref].supabase.co:6543/postgres?pgbouncer=true
DB_MAX_CONNECTIONS=20

# Migrations & one-off tasks (direct — port 5432):
# DATABASE_URL=postgresql://postgres:password@db.[ref].supabase.co:5432/postgres
```

**Important**: PgBouncer in transaction mode doesn't support:
- `SET` statements
- Prepared statements with session-level parameters
- `LISTEN`/`NOTIFY`

Your raw `pg` parameterized queries are fine. Avoid session-level features.

### Verify

```bash
# Connect via pooler
psql "postgresql://postgres:password@db.[ref].supabase.co:6543/postgres?pgbouncer=true"
# Should connect and run queries
```

## Step 5: Set Up Database Monitoring & Alerts

### What

Configure monitoring in the Supabase dashboard so you know when things go wrong before users do.

### Action

1. **Supabase Dashboard** → Project → Project Settings → Alerts
2. Set up email/Slack notifications for:
   - CPU > 80%
   - Disk > 80%
   - Connections > 80% of limit

3. **Supabase Dashboard** → Database → Query Performance
   - Review periodically for slow queries
   - Look for sequential scans on large tables

4. **Supabase Dashboard** → Database → Database Health
   - Check daily for blocking queries, long-running transactions

### Verify

- [ ] Test an alert by temporarily spiking CPU or connections
- [ ] Confirm the notification channel works (email/Slack)

## Step 6: Set Up Automated Backups

### What

Ensure database backups are configured so you can recover from accidents.

### Action

**Supabase Pro** includes:
- **Daily backups**: Automatic, 7-day retention — enabled by default
- **Point-in-Time Recovery (PITR)**: Optional add-on (~$15/mo extra)

**To verify**:
1. Supabase Dashboard → Database → Backups
2. Check that backups are running and have a recent timestamp
3. Download a manual backup before any major schema change

**Before schema changes** — always take a manual backup:
```
Supabase Dashboard → Database → Backups → Download Full Backup
```

### 🗣️ Input Needed

- Do you need PITR? (Recommended if data loss is unacceptable — e.g., user credits, payment records)
- What's your RPO (Recovery Point Objective)? Daily backup = up to 24h data loss. PITR = seconds.

## Step 7: Configure Connection Pool for Production

### What

Tune your `pg.Pool` configuration for production workloads.

### Recommended settings

```ts
const poolConfig = {
  connectionString: databaseUrl,
  max: parseInt(process.env.DB_MAX_CONNECTIONS || '20', 10),  // Increased for prod
  idleTimeoutMillis: 60000,    // 60s — longer for prod to reuse warm connections
  connectionTimeoutMillis: 5000,
  ssl: ssl ? { rejectUnauthorized: false } : false,
};
```

### Why these values

| Parameter | Dev | Prod | Rationale |
|-----------|-----|------|-----------|
| `max` | 5-10 | 20-25 | Prod needs more concurrent connections |
| `idleTimeoutMillis` | 30000 | 60000 | Prod benefits from keeping connections warm |
| `connectionTimeoutMillis` | 5000 | 5000 | Fail fast if DB is down |

### Verify

- [ ] App starts and handles concurrent requests without connection errors
- [ ] Pool doesn't exhaust the Supabase connection limit (check Supabase dashboard)

## Step 8: Test Failover & Resilience

### What

Verify your app handles database outages gracefully — don't let a Supabase hiccup take down your entire app.

### Test scenarios

| Scenario | What to test | Expected behavior |
|----------|-------------|-------------------|
| DB unreachable | Stop the API server | API returns 5xx, frontend shows error state (not blank page) |
| Slow queries | Run an expensive query | Connection timeout fires, query fails fast (5s) |
| Connection exhaustion | Spike connections | PgBouncer queues, app waits, eventually times out |
| Pool restart | Kill and restart API | Pool reconnects, no manual intervention needed |

### Action

Your `db.ts` already has:
```ts
pool.on('error', (err) => {
  console.error('Unexpected error on idle PostgreSQL client', err);
});
```
This prevents the app from crashing on idle connection errors. Good.

Consider adding:
- A health endpoint that checks DB connectivity (not just returns 200)
- Retry logic for transient failures (e.g., `npm install promise-retry`)

### What

Create an `ops/` reference doc so you (or anyone else) can look up the production database configuration without spelunking through dashboards.

### Template

```markdown

- **SSL**: Required

## Pool Configuration

- **Idle timeout**: 60s

- **Schedule**: Daily (automatic)
- **Retention**: 7 days
- **PITR**: Enabled/Disabled

## Monitoring
- **Alerts**: CPU > 80%, Disk > 80%, Connections > 80%

1. Make changes in `schema.sql` or create a migration file
```

## Learning Log

> As we go through this process for each project, we append learnings here.

### 2026-07-08 — ViewCreator Initial Setup

| Learning | Detail |
|----------|--------|
| **Hostname sniffing** | The project had `databaseUrl.includes('supabase.co')` — one line, but it's the only vendor coupling. Removed it in favor of `DB_SSL` env var. The old logic also had a subtle bug: `sslMode !== 'false'` meant any env var value except 'false' would enable SSL. Cleaned up to exact `=== 'true'` and `=== '1'` checks. |
| **PgBouncer port** | Supabase pooler uses port 6543, direct uses 5432. Easy to miss. Documented in env setup. |
| **Migration system** | The project used a single `schema.sql` with `IF NOT EXISTS`. Works but not ideal for complex schema changes. Better to use proper versioned migrations (Supabase CLI or a migrations table). |
| **Connection pool sizing** | Dev needed `max: 5`, prod needs `max: 20` with PgBouncer. Different envs, different configs. |
| **No Supabase SDK** | The project uses raw `pg` — no Supabase client. This means zero lock-in and simpler debugging. The Supabase skill advice about RLS and Data API doesn't apply since we only connect via backend. |
| **Error message update** | Updated the `DATABASE_URL` error message to be provider-agnostic — removed the Supabase-specific example. A small thing, but it signals to developers that this code works with any Postgres host. |
| **`.gitignore` gotcha** | The `.env*` glob pattern also ignores `.env.example` files. Need to add `!.env.example` exception to track them. Standard practice: list `.env`, `.env.local`, `.env.*.local` explicitly instead of using `.env*`. |
| **`.env.example` never committed** | Checked: the package-level `.env.example` files were never tracked by git because `.env*` ignored them. They existed only locally. Force-add needed for first commit. |
| **Root `.env` consolidation** | Moving from 3 `.env` files (api, database, ui) to 1 root `.env`. API and database packages load root via `dotenv.config({ path: '../.env' })`. UI keeps `.env.local` (Next.js convention). |
| **`dotenv.config()` fallback** | `db.ts` already had `dotenv.config()` + `dotenv.config({ path: '../.env' })` — the second call doesn't overwrite already-set vars. Added same pattern to `index.ts`. |

## When to Deviate From This Playbook

| Situation | What to change |
|-----------|---------------|
| Using Supabase SDK (`@supabase/supabase-js`) instead of raw `pg` | Add RLS step, Data API configuration, service_role key handling |
| Using Supabase Auth instead of Clerk | Replace Clerk steps with Supabase Auth setup |
| Using managed Postgres (RDS, Cloud SQL) instead of Supabase | Skip pooler step, add VPC/network config, handle SSL certs differently |
| Deploying to GCP instead of AWS | Use Cloud SQL + GCS instead of RDS + S3 |
